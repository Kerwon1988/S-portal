## Convenciones y límites

- S-portal es MVC server-side: páginas y formularios devuelven HTML, redirect o fragmento HTMX. No se propone una API JSON pública interna, salvo `POST /api/telemetry/errors`. La API M2M es saliente y solo se especifica conforme a [05-integracion-simbiosphere.md](05-integracion-simbiosphere.md).
- Las rutas con `/{lang}` representan `es` o `en`. La ruta pública tiene locale en URL; el área privada usa perfil → cookie → `Accept-Language`.
- **SUPUESTO** identifica método, campo, status HTTP, nombre de ruta o decisión no cerrado literalmente en una fuente. Las acciones POST/HTMX son propuestas MVC convencionales: siempre CSRF; no son API pública.
- Errores MVC: conservar el formulario/fragmento con errores asociados y datos no sensibles; 403 para permiso ausente; 404 o respuesta equivalente para recurso ajeno según política anti-IDOR del módulo; 409/422 para transición o estado no válido donde lo indica [07-seguridad-rgpd.md](07-seguridad-rgpd.md). El status concreto de validación de formularios queda **SUPUESTO** hasta fijar una convención común.
- La validación en servidor es obligatoria. Solo las claves/namespaces de módulo están delimitados aquí; las claves concretas ES/EN y los nombres definitivos de DTOs no aparecen aprobados en las fuentes y no se inventan.
- Módulo owner indica quién mantiene el caso de uso y sus rutas; no autoriza el acceso a entidades/repositorios de otros módulos. Las colaboraciones usan `api`/SPI.
- Contratos de entidades omitidos por tratarse de comportamiento interno. Los tests se referencian como `TC-<ID>` según el catálogo, con el tipo de prueba descrito en la ficha.

## Gaps que requieren decisión/refinamiento

1. **Métodos y status MVC:** los documentos fijan la semántica UI/seguridad, pero no una tabla HTTP por cada handler ni una convención uniforme de `400` frente a `422`, PRG, redirects post-login o 403/404 anti-IDOR. Mantener como propuesta hasta cerrar en fichas/contratos de cada tarea.
2. **Formularios/DTOs:** varios requisitos solo describen el comportamiento. Faltan nombres exactos y límites de campos de registro, contacto, cuenta, solicitud, edición de usuario, presupuesto, comentarios, filtros y acciones. En particular, el contrato de contacto no cierra campos obligatorios de remitente anónimo.
3. **Rutas no fijadas:** logout, preview/restauración/publicación CMS, edición legal, invitación de trabajador, acciones de solicitud/asignación/estado/presupuesto, adjuntos/audio, continuación mágica, gestión de aprovisionamientos y endpoints exactos Actuator. No cristalizar paths propuestos sin que la ficha los confirme.
4. **i18n:** se conoce el bundle por módulo y ES/EN; faltan las claves concretas de formulario, estado y error. Los equipos deben añadir ambas traducciones junto con cada ruta.
5. **Negocio/legal pendiente:** aprobación de textos legales, copy de gratuidad y condiciones/IVA; países/NIF; número WhatsApp/email de contacto; SLA; política de privacidad/retención y reglas finales de estados/cancelación/cierre. Consultar [13-preguntas-abiertas.md](13-preguntas-abiertas.md); no publicar valores SUPUESTO como compromisos.
6. **SIM-012:** el vínculo de cuenta existente se diseña en MVP, pero su implementación es R2; no se añade una ruta de vinculación manual al MVP. SIM-014 añade selector en sugerencia tras SIM-006 y solo muestra negocios del titular.
7. **Alcance posterior:** sin ruta MVP para notificaciones in-app, pagos, respuesta por email, sincronización de ciclo de vida SimbioSphere, selector de módulos completo, IA, SSO, APIs públicas de negocio o CRUD de catálogo DEMO.
8. **Ruta pública del CMS:** `/{lang}/{slug}` debe reservar las rutas fijas de producto/contacto/legal y confirmar precedencia/colisiones con slugs en CMS-004.

### Paralelismo sin colisión

- Los carriles `content`, `identity`, `customer`, `staff`, `request`, `messaging`, `notification`, `files`, `audit` y `simbiosphere` pueden avanzar en sus paquetes, templates propias, bundles del módulo y migraciones owner una vez satisfecho su DAG del [roadmap](10-roadmap-backlog.md).
- Requieren integración coordinada antes de modificar: rutas/seguridad global (`config`), layouts/fragments compartidos, SPIs en `shared`, build/migraciones/gates comunes, `docs/INVENTARIO.md`, `README`/`DIARIO`, ADRs, este contrato y configuración global de i18n.
- F0, CMS/identity de F1 y los carriles de F2–F5 tienen dependencias explícitas: este mapa no las libera. La habilitación debe comprobarse por tarea en el roadmap y su ficha.
- El contrato externo SIM-002 es una superficie de trabajo compartida entre owners Portal y DEMO; la pista DEMO es distinta y queda fuera de este cambio de documentación del portal.
